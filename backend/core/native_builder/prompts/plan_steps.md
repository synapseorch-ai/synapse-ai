Each step has an `id` (short snake_case, unique), a `type`, a `name` a person reads, and `does` (one sentence). By type:
- `agent`: an agent works with its tools; `agent` is a new agent's name from `agents` or an existing agent's id; `prompt` is what it is asked.
- `llm`: one model call with no tools, for writing or reshaping text; `prompt` is the instruction.
- `tool`: calls one tool; `tool` is its exact name. When its inputs are known, set them in `config.tool_arguments` and no model is called: fixed values, or what an earlier step wrote as `{{state.<step id>}}`, e.g. `{"city": "Rotterdam"}` or `{"text": "Today: {{state.check_weather}}"}`, and `{}` when it takes none. Left out, a model reads the run so far and fills them in. Known means the person said it, this workspace holds it or a lookup found it: an address of theirs (their site, an email, an account, who gets it) is never guessed, and code asks about one the run was never given.
- `human`: waits for a person; `prompt` is what they are asked. A check the person wants before something goes out ("a summary I can check before it goes to the client") is a human step right before the step that sends it. Its answer is an object: with no `config.human_fields`, the person's yes or no, `{approved, feedback}`, never text to read; for text from them (what a schedule's or a webhook's run needs from its person), set `config.human_fields`, e.g. `[{"name": "request", "type": "textarea", "label": "The request"}]`, and its answer is `{"request": <their text>}`.
- `if_else`: `condition` is an expression over what earlier steps wrote, read by their step ids, e.g. `state.check_weather.wind_kmh > 40`; `branches` are `{"true": id, "false": id}`.
- `switch`: `condition` is such an expression; `branches` map each of its values to a step id, plus `default`. {{EXPRESSION_VOCABULARY}}
- `evaluator`: a model judges and picks a branch; `prompt` says how to judge, `branches` map each label to a step id. Use it only where the choice is a judgement in words.
- `loop`: `body` lists the step ids run each time, one after another; `loop_over` names the step whose output is the list, e.g. `fetch_emails`. Nothing inside a body branches: branch after the loop, on what it wrote.
- `parallel`: `body` lists the branches' first step ids; they meet at a `merge` step.
- `workflow`: runs another workflow, by an existing workflow's id or a title from `inner_workflows`, which are saved first.
- `retrieve` / `ingest`: search or fill knowledge bases, named by id in `config`.
- `transform`: Python in `config.transform_code`, only where the workspace runs code. It reads earlier steps as `state.<step id>`, each what that step wrote: an `llm` or `agent` step's text; a `human` step's answer, an object, read by its field (`state.review.feedback`), never as text; a `tool` step's answer: when the tool answers JSON and your code reads its fields (`state['<step id>']['name']`, `.get('name')`) or goes through it (`for`, `len`, `[0]`), it is parsed for you; otherwise it is the tool's text. It puts its answer in `result` (`result = ...`, never `return`). It reaches no service and reads no key: a service is a `tool` step. It reads a Vault file itself with `read_vault("path/in/vault.csv")`, the path written out; a `vault_read` step's answer in state is JSON `{"path", "content"}`, not the file.
- `end`: ends the run.
A step with no `next` goes on to the next step in the list, and the last one ends the run. A step's output is kept under its id, which is how later steps and conditions read it. The run's own message, what it was started with (the person's ask, a schedule's or a webhook's input), is `state.user_input`: a step reads it there, and no step asks a person for it again.
