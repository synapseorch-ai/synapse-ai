Each step has an `id` (short snake_case, unique), a `type`, a `name` a person reads, and `does` (one sentence). By type:
- `agent`: an agent works with its tools; `agent` is a new agent's name from `agents` or an existing agent's id; `prompt` is what it is asked. When a later step reads fields of its answer, it sets `config.output_fields` as an `llm` step does.
- `llm`: one model call with no tools, for writing, reshaping or judging text; `prompt` is the instruction. Its answer is text. When a later step reads fields of it (a condition, a template, code), set `config.output_fields`: a list of `{"name", "type", "description"}`, each type `boolean` (a yes or no), `choice` with `options` (one of a few labels, e.g. `["urgent", "normal"]`), `number`, `list` (of text) or `text`; for a nested answer, `"object"` with its own `fields`, or `list` with `"of": {"fields": [...]}` for a list of groups, e.g. `{"name": "leads", "type": "list", "of": {"fields": [{"name": "email", "type": "text"}]}}`, read as `state.<step id>.leads.0.email` or by a loop over `state.<step id>.leads`. The run asks the model for that object and holds it to it, and a later step reads `state.<step id>.<field>`; never an `extract_json` step after it, and a decision on it is never read out of its words (`.startswith(…)`, `in`, `== 'URGENT'`). An llm step never reads a page, a crawl or a file a Tool step fetched: that can be too long and is then a file only an agent step can read, so use an agent step there.
- `tool`: calls one tool; `tool` is its exact name. When its inputs are known, set them in `config.tool_arguments` and no model is called: fixed values, or what an earlier step wrote as `{{state.<step id>}}`, e.g. `{"city": "Rotterdam"}` or `{"text": "Today: {{state.check_weather}}"}`, and `{}` when it takes none. Left out, a model reads the run so far and fills them in. Known means the person said it, this workspace holds it or a lookup found it: an address of theirs (their site, an email, an account, who gets it) is never guessed, and code asks about one the run was never given. Reach the source the person names: told a CRM they use, a shared drive or a database, the plan reaches that one (that CRM's tool, that drive's file, that database's connection); an existing tool is used only when it reaches that same source and is connected (its key on its card), never another source's tool because it returns the same kind of data. To add a line or an entry to a Vault file (a log), call `vault_write` with `"append": true` in `config.tool_arguments`: it adds at the end and creates the file on the first run; never read the file first only to add to it.
- `human`: waits for a person; `prompt` is what they are asked. A check the person wants before something goes out ("a summary I can check before it goes to the client") is a human step right before the step that sends it. Its answer is an object of its `config.human_fields` by name, read as `state.<step id>.<field>`; with no `config.human_fields`, the person's words, which have no fields to read. A yes or no a later step branches on is a yes/no field, `[{"name": "approved", "type": "boolean", "label": "Approve?"}]`, which the run asks with Approve and Decline, read as `state.<step id>.approved`; add `{"name": "feedback", "type": "textarea", "label": "What to change"}` when a later step reads what they said; for text from them (what a schedule's or a webhook's run needs from its person), set `config.human_fields`, e.g. `[{"name": "request", "type": "textarea", "label": "The request"}]`, and its answer is `{"request": <their text>}`.
- `if_else`: `condition` is an expression over what earlier steps wrote, read by their step ids, e.g. `state.check_weather.wind_kmh > 40`, and on a model's answer one of its `config.output_fields`, e.g. `state.review_diff.risky`; `branches` are `{"true": id, "false": id}`.
- `switch`: `condition` is such an expression; `branches` map each of its values to a step id, plus `default`. {{EXPRESSION_VOCABULARY}}
- `evaluator`: a model judges and picks a branch; `prompt` says how to judge, `branches` map each label to a step id. Use it only where the choice is a judgement in words.
- `loop`: `body` lists the step ids run each time, one after another; `loop_over` names the step whose output is the list, e.g. `fetch_emails`. Nothing inside a body branches: branch after the loop, on what it wrote.
- `parallel`: `body` lists the branches' first step ids; they meet at a `merge` step.
- `workflow`: runs another workflow, by an existing workflow's id or a title from `inner_workflows`, which are saved first.
- `retrieve` / `ingest`: search or fill knowledge bases, named by id in `config`.
- `transform`: Python in `config.transform_code`, only where the workspace runs code. It reads earlier steps as `state.<step id>`, each what that step wrote: an `llm` or `agent` step's text; a `human` step's answer, an object of its `config.human_fields`, read by its field (`state.review.feedback`), never as text; a `tool` step's answer: when the tool answers JSON and your code reads its fields (`state['<step id>']['name']`, `.get('name')`) or goes through it (`for`, `len`, `[0]`), it is parsed for you; otherwise it is the tool's text. It puts its answer in `result` (`result = ...`, never `return`). It reaches no service and reads no key: a service is a `tool` step. It reads a Vault file itself with `read_vault("path/in/vault.csv")`, the path written out; a `vault_read` step's answer in state is JSON `{"path", "content"}`, not the file.
- `end`: ends the run.
A step with no `next` goes on to the next step in the list, and the last one ends the run. A step's output is kept under its id, which is how later steps and conditions read it. The run's own message, what it was started with (the person's ask, a schedule's or a webhook's input), is `state.user_input`: a step reads it there, and no step asks a person for it again.
A tool answers what its `outputSchema` in the tools list declares: read it before planning what a step does with the answer, and never assume a field it doesn't list. An `llm` or `agent` step whose prompt reads a tool step's whole answer names in `uses_fields` each field of it that it uses, as `<step id>.<field>`. When they asked for something no tool here answers, plan a tool that does, or list that part in asked as not_done, with why_not.
A step's prompt, its `does` and an agent's `purpose` keep the person's own words for what to count, filter or pick: "open tickets" stays "open tickets", never "unresolved issues". Where such a word could mean more than one value the source shows (a priority, a plan tier), use the source's exact value when a read or lookup showed it; otherwise ask the person which.
